## Context

当前首页以工程初始化说明为主，虽然满足“最小可运行”的目标，但不能支持设备管理场景。新需求要求首页直接呈现设备列表，并在主操作区提供“添加设备”按钮，点击后展示底部抽屉，让用户看到后续即将支持的设备添加方式。

由于本次不实现真正的配网和绑定逻辑，设计重点在于信息层级、交互清晰度以及后续接入功能时的可扩展性，而不是数据接入复杂度。

## Goals / Non-Goals

**Goals:**
- 首页以设备列表为主视图，能够清晰区分设备名称、位置与在线状态。
- “添加设备”按钮在首屏显眼可见，点击后有明确的底部抽屉反馈。
- 抽屉中展示四个操作项，并支持取消关闭与遮罩关闭。
- 页面结构便于后续把抽屉选项接入真实业务逻辑。

**Non-Goals:**
- 不接入真实设备数据源，本次可使用静态设备列表。
- 不实现扫一扫、蓝牙配网或绑定设备的业务流程。
- 不新增 tabBar、多页面跳转或后台接口调用。

## Decisions

### 决策一：使用静态设备数据驱动首页展示
- 方案：将设备列表和抽屉选项配置放入 `utils/`，页面直接读取并渲染。
- 原因：当前目标是先完成首页结构和交互，不引入接口状态管理可以保持改动聚焦。
- 备选方案：直接在页面文件中内联所有数据。
- 不采用原因：后续接入真实数据时难以替换，也不利于保持页面文件简洁。

### 决策二：使用原生视图组合模拟底部抽屉
- 方案：基于遮罩层和底部面板实现抽屉弹窗，通过页面状态控制显示与隐藏。
- 原因：微信小程序原生能力足以覆盖当前需求，且不会引入额外依赖。
- 备选方案：使用 `action-sheet` 或第三方弹层组件。
- 不采用原因：`action-sheet` 可定制空间有限，第三方组件超出当前轻量工程目标。

### 决策三：首页强调主操作与设备概览并存
- 方案：页面上方展示标题和“添加设备”按钮，中部展示设备统计，主体区域展示设备卡片列表。
- 原因：这样可以同时满足“显眼入口”和“设备列表首页”的两类要求，信息层级更直观。
- 备选方案：仅展示设备列表，在底部悬浮一个按钮。
- 不采用原因：悬浮按钮虽然直接，但在当前简洁页面中会削弱设备概览区域的组织性。

## Risks / Trade-offs

- [风险] 静态数据页面与真实业务接入存在差距。 → 缓解：将列表数据与抽屉配置独立到 `utils/`，降低后续替换成本。
- [风险] 自定义抽屉需要处理遮罩、点击关闭与层级样式。 → 缓解：保持交互单一，仅支持打开、关闭和按钮点击提示。
- [风险] 四个入口当前没有实际功能，用户可能误以为可用。 → 缓解：在点击操作项时提供“暂未开放”的明确反馈。

## Migration Plan

1. 替换首页静态初始化内容，改为设备列表页面结构。
2. 增加“添加设备”按钮和底部抽屉显示逻辑。
3. 将设备数据与抽屉选项抽离为可复用配置。
4. 验证页面加载、抽屉开关和提示文案符合预期。
