## Context

当前 `mini-app` 仓库只有 OpenSpec 目录，没有实际的微信小程序工程文件，导致开发者无法在微信开发者工具中直接导入和运行项目。此次设计需要在保持初始化范围可控的前提下，建立一个最小可用、可扩展的小程序基础工程，并为后续页面、组件和接口能力提供一致的目录与配置约束。

约束包括：
- 工程应兼容微信开发者工具的标准项目结构。
- 初始内容应尽量精简，优先保证可运行与可扩展，而不是一次性引入复杂工程体系。
- 文档与规范需要和 OpenSpec 变更保持同步，便于后续继续用 spec 驱动迭代。

## Goals / Non-Goals

**Goals:**
- 提供一个可以被微信开发者工具直接打开的基础小程序项目。
- 建立应用入口、至少一个初始页面、全局样式和项目配置文件。
- 明确依赖安装、启动说明和后续扩展入口，降低后续功能开发成本。

**Non-Goals:**
- 不在本次初始化中引入完整的业务页面、远程接口或状态管理方案。
- 不强制绑定特定 UI 组件库或复杂工程化框架。
- 不处理上线发布、分包优化或多环境配置等后续阶段问题。

## Decisions

### 决策一：采用微信原生小程序标准目录作为首个落地版本
- 方案：使用 `app.*`、`pages/`、`utils/`、`project.config.json` 等标准结构初始化项目。
- 原因：这是微信开发者工具兼容性最稳定的路径，学习和维护成本最低，也最适合作为后续是否引入增强框架前的基线。
- 备选方案：直接引入 Taro、uni-app 等跨端框架。
- 不采用原因：当前需求是“初始化微信小程序项目”，优先交付最小可运行骨架，而不是在启动阶段增加框架决策和构建复杂度。

### 决策二：先提供一个最小首页，而不是空工程
- 方案：默认提供一个首页页面，用于验证路由、样式、配置和运行链路已完整打通。
- 原因：空工程虽然也可导入，但缺少直观的验收载体；提供首页可以让初始化结果立即可见、可测试。
- 备选方案：只提供应用入口与配置，不提供页面。
- 不采用原因：不利于快速确认初始化是否成功，也无法沉淀最小页面示例。

### 决策三：依赖与脚本约定保持轻量
- 方案：仅加入必要的 `package.json` 与开发说明，避免引入与微信原生结构耦合度低的复杂工具链。
- 原因：初始化阶段核心是统一项目起点，而不是完善全部研发体验。
- 备选方案：同时接入 lint、format、测试框架和 CI。
- 不采用原因：这些能力可以在工程骨架稳定后按独立变更补充，避免首次初始化范围膨胀。

## Risks / Trade-offs

- [风险] 原生结构虽然简单，但后续若切换到跨端框架会出现迁移成本。 → 缓解：当前目录划分保持清晰，把业务代码集中到页面与公共目录，减少未来替换成本。
- [风险] 初始工程过于精简，可能无法覆盖团队后续全部开发习惯。 → 缓解：通过 OpenSpec 继续增量补充工程规范，而不是在首次初始化中提前做过多假设。
- [风险] 本地运行依赖微信开发者工具，CLI 验证能力有限。 → 缓解：在任务中明确要求补充导入和运行说明，并以基础页面可见作为验收条件。

## Migration Plan

1. 在 `mini-app` 根目录创建微信小程序基础工程文件。
2. 补充项目说明，使开发者可以安装依赖并在微信开发者工具中导入项目。
3. 使用最小首页验证项目能够正常启动和展示。
4. 若初始化方案不满足预期，可回滚新增工程文件并保留 OpenSpec 文档，用于重新调整初始化策略。

## Open Questions

- 团队后续是否计划切换到增强框架，以便提前评估目录兼容策略。
